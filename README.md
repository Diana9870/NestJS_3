# Cinema API (MongoDB)

Серверна частина кінотеатру на NestJS: фільми, зали, сеанси та бронювання місць.
Це третя робота курсу: той самий сервіс, що в ДЗ №2, переїхав з PostgreSQL (TypeORM) на MongoDB (Mongoose). Зовнішня поведінка маршрутів та сама, змінилися модель даних і спосіб захисту від подвійного бронювання.

## Встановлення залежностей

```bash
npm install
```

## Змінні середовища

Скопіюй `.env.example` у `.env` і за потреби зміни значення. Файл `.env` у репозиторій не потрапляє.

```bash
cp .env.example .env
```

Приклад `.env`:

```env
# Port the HTTP server listens on
PORT=3000

# Runtime environment label (development | production | test)
NODE_ENV=development

# MongoDB connection string. The database name is the last path segment.
# Docker Compose publishes MongoDB on localhost:27017 without authentication.
MONGODB_URI=mongodb://localhost:27017/cinema
```

Змінні читає `ConfigModule`, перевіряє клас `EnvironmentVariables` (`src/config/env.validation.ts`, декоратори class-validator). Якщо `MONGODB_URI` бракує або вона не схожа на рядок підключення MongoDB, застосунок не стартує й виводить список проблем. `PORT` і `NODE_ENV` необов'язкові. Підключення виконує `MongooseModule.forRootAsync`, рядок береться з `ConfigService`, а не з `process.env`.

## Підняття MongoDB (Docker Compose)

```bash
docker compose up -d
```

Піднімає MongoDB 7 з `docker-compose.yml` на `localhost:27017` (порт можна змінити змінною `MONGO_PORT` у `.env`; тоді змінися і порт у `MONGODB_URI`). Дані зберігаються в томі `cinema_mongodata`. Зупинити: `docker compose down` (з `-v` ще й видалить дані). Replica set не потрібен: транзакцій сервіс не використовує.

## Запуск у режимі розробки

```bash
npm run start:dev
```

Сервіс стартує на `http://localhost:3000` (порт береться зі змінної `PORT`).
Swagger-документація: `http://localhost:3000/docs`.

Інші команди: `npm run build` (збірка в `dist/`), `npm run start:prod` (запуск зібраного коду).

Повний порядок з нуля:

```bash
npm install
cp .env.example .env
docker compose up -d
npm run seed          # необов'язково
npm run start:dev
```

## Засівання бази даних

```bash
npm run seed
```

Запускає `src/seed.ts` на порожній базі: 2 фільми, 2 зали (`Hall 1` на 8×12 місць, `Hall 2` на 3×5), 4 сеанси в різні дати (завтра, післязавтра, через 3 і через 7 днів) і 1 бронювання з двох місць (ряд 4, місця 6 і 7 на першому сеансі). Повторний запуск дублікатів не створює: кожен документ має фіксований `_id` і записується через upsert з `$setOnInsert`, зал спершу шукається за унікальною назвою.

## Перевірка запитами

Файл `requests.http` у корені містить запити до всіх маршрутів і до кожної описаної помилки. Він написаний для розширення [REST Client](https://marketplace.visualstudio.com/items?itemName=humao.rest-client) у VS Code: виконуй запити послідовно згори вниз (`Send Request` над кожним). Порядок: фільм, зал, сеанс, бронювання, потім видалення. Ідентифікатори підставляються зі змінних з відповідей попередніх запитів (`{{createFilm.response.body.id}}` тощо), вручну нічого вписувати не треба. Для помилок 404 і 400 у файлі є змінні `@missingId` (коректний за формою, але неіснуючий ObjectId) і `@badId` (некоректний за формою). Дати сеансів стоять у 2099 році, назви залів рандомізовані, тому файл можна проходити повторно.

## Структура

```
docker-compose.yml   MongoDB для розробки
requests.http        запити до всіх маршрутів і помилок
src/
  main.ts            запуск, Swagger на /docs
  app.module.ts      корінь: ConfigModule, MongooseModule.forRootAsync, глобальні ValidationPipe і фільтр винятків
  seed.ts            засівання бази (npm run seed)
  config/            клас змінних оточення з валідацією
  common/            pipe для ObjectId у :id, декоратори DTO і Swagger, фільтр винятків, DTO помилки
  films/             фільми: схема, DTO, сервіс, контролер
  halls/             зали, обчислення переліку місць (seat-layout.ts)
  showings/          сеанси: схеми з вкладеними місцями й бронюваннями, пагінація, карта місць
  bookings/          бронювання: запис і скасування одним оновленням документа сеансу
```

Кожна колекція описана класом зі `@Schema` і `@Prop` у `schemas/`, моделі підключені в feature-модулях через `MongooseModule.forFeature`. Сервіси працюють лише через моделі Mongoose, до драйвера MongoDB напряму сервіси не звертаються.

## Модель даних і чому місця й бронювання лежать усередині сеансу

Три колекції: `films`, `halls`, `showings`. Таблиці `bookings` і `booking_seats` з ДЗ №2 зникли: сеанс зберігає масив своїх місць `seats` (`row`, `seat`, `bookingId` або `null`) і масив своїх бронювань `bookings` (`_id`, `seats`, `totalPrice`, `createdAt`). Вкладені документи описані окремими класами зі своїми схемами (`ShowingSeat`, `BookedSeat`, `ShowingBooking`).

**Причина: неподільність.** У PostgreSQL бронювання було двома діями (рядок бронювання і рядки місць) в одній транзакції, а правило «місце не продають двічі» тримав унікальний індекс. У MongoDB неподільне саме оновлення одного документа. Зміна кількох документів однією операцією потребувала б транзакції, а транзакція потребує replica set. Якщо і місця, і бронювання лежать усередині документа сеансу, то обидві дії стають одним `updateOne`, і транзакція не потрібна.

Як це працює (`src/bookings/bookings.service.ts`):

- фільтр оновлення містить `$and` з `$elemMatch { row, seat, bookingId: null }` для кожного потрібного місця, тож документ проходить фільтр лише тоді, коли **всі** місця вільні;
- секція оновлення одночасно проставляє `bookingId` у ці елементи `seats` (`$set` із позиційним оператором `$[target]` та `arrayFilters`) і додає бронювання в `bookings` (`$push`);
- якщо хоча б одне місце зайняте, фільтр нічого не знаходить, документ не змінюється, `matchedCount` дорівнює 0, і сервіс повертає 409;
- два паралельні запити на те саме місце виконуються послідовно, другий отримує `matchedCount` 0;
- читання документа з перевіркою масиву в коді й подальшим записом немає: між читанням і записом інший запит міг би зайняти те саме місце.

До оновлення перевіряється те, чого фільтр розрізнити не може: існування сеансу (404), межі залу (400: інакше неіснуюче місце дало б 409) і унікальність пар `row`/`seat` у запиті (400: два однакові місця в `$and` задовольняються одним вільним місцем, і в `bookings` потрапили б два записи на одне крісло з подвоєною ціною; це робить `@ArrayUnique` у DTO). Скасування (`DELETE /bookings/:id`) теж одне оновлення: сеанс шукається за `bookings._id`, `$set` повертає `null` у місця з цим `bookingId`, `$pull` видаляє бронювання.

Перелік місць у бронюванні дублює масив `seats`: так бронювання віддається без перебору всіх місць залу. Джерело істини про зайнятість — `seats`.

**Межа застосовності.** Вкладати дані в документ можна, коли їхня кількість обмежена. Місць у залі кілька сотень, бронювань на сеанс не більше, ніж місць, тож документ сеансу не росте безмежно. Щоб це лишалося правдою, розмір залу обмежений 100 рядами по 100 місць (до 10 000 елементів, це далеко від ліміту 16 МБ на документ). Якби бронювання накопичувалися роками без обмеження, вкладення не підійшло б.

## Рішення, які варто знати

- **Ідентифікатори.** Усі id — ObjectId (24 шістнадцяткові символи). `ParseObjectIdPipe` для `:id` і декоратор `@IsObjectIdString()` для тіла та query (`filmId`, `hallId`) перевіряють форму до звернення до бази: некоректний id дає **400** з поясненням формату, коректний за формою id неіснуючого документа дає **404**. Формат перевіряється регулярним виразом, бо `isValidObjectId` з Mongoose пропускає будь-який рядок із 12 символів.
- **Відповіді.** Документи перетворюються на відповідь класами DTO (`FilmResponseDto.from(...)` тощо): `_id` віддається рядком `id`, внутрішній ObjectId у тіло не потрапляє. Поле `bookingId` та інші ObjectId усередині документів назовні не віддаються.
- **Розподіл перевірок.** DTO (class-validator) перевіряють форму: наявність поля, тип, діапазон, формат, унікальність місць у запиті. Сервіси перевіряють доменні правила, яким потрібен стан бази: існує чи фільм і зал, чи місце є в залі, чи є залежні сеанси, чи час у майбутньому. `ValidationPipe` глобальний (`whitelist` + `transform`).
- **Унікальність назви залу.** Унікальний індекс описаний у схемі (`HallSchema.index`) і має collation рівня 2, тобто не залежить від регістру: «Hall 1» і «hall 1» це одна назва, як у ДЗ №2. Дублікат відхиляє сама база (код 11000), це стає 409, у тому числі для двох одночасних запитів.
- **Видалення фільму чи залу.** У MongoDB немає зовнішніх ключів, тому сервіс запитом перевіряє, чи є сеанс, що посилається на фільм або зал, і тоді повертає 409. Між перевіркою й видаленням теоретично можливий проміжок (сеанс створили саме в цю мить); для цього завдання він прийнятий.
- **Створення сеансу.** Сервіс бере зал, розгортає `rows` і `seatsPerRow` у масив `seats` (кожен `bookingId: null`) і кладе його в документ; `bookings` починається порожнім. Фільм або зал, яких немає, дають 400 з назвою причини. Відповідь не містить масивів `seats` і `bookings`.
- **`GET /showings`.** Відповідь: `{ items, total, page, limit }`. `items` — сеанси поточної сторінки з `filmTitle` і `hallName` (їх розкриває `populate`); масиви `seats` і `bookings` виключені проєкцією, тож на сторінку вантажаться лише легкі документи. Фільтр (`filmId`, `date`), сортування (`startsAt`, потім `_id`), `skip` і `limit` виконує запит до бази, `total` рахує `countDocuments` з тим самим фільтром. Межі доби в `date` — UTC.
- **Час початку.** `startsAt` має містити дату й час у розширеному форматі (`2099-01-01T18:00:00Z`); значення без зсуву читається як UTC. У базі зберігається момент часу (тип Date), у відповіді він повертається в UTC (`2099-01-01T18:00:00.000Z`). На відміну від ДЗ №2, початковий текст зі зсувом (`+03:00`) окремо не зберігається.
- **`GET /bookings`** збирає бронювання з усіх сеансів агрегацією (`$unwind` по `bookings`), порядок за часом створення. **`GET /showings/:id/seats`** будує відповідь з масиву `seats` сеансу, `isBooked` обчислюється з `bookingId`.
- **Єдиний формат помилок.** `AllExceptionsFilter` віддає для кожної помилки `{ "statusCode", "message", "path" }`. Непередбачена помилка (наприклад, обрив підключення до бази) дає 500 із загальним повідомленням, а подробиці лише пишуться в лог.
- Гроші: ціни та `totalPrice` у копійках, цілими числами. Ділення на сто виконує клієнт.
- Додаткові обмеження DTO, яких немає в завданні: `title` до 255 символів, `releaseYear` від 1888 до 2100, назва залу до 100 символів, зал до 100 рядів і 100 місць у ряду (див. вище), не більше 1000 місць в одному бронюванні.
